# Provenance

Meridian-MCP began as a non-ancestral import of [`imcynic/dm-mcp`](https://github.com/imcynic/dm-mcp) at source commit `6a739a4278b53e86b430abaf011467f22c9dd2ec`. The import did not preserve that repository's Git ancestry. The original repository is a provenance reference, not an implementation authority.

The local history begins at `d6ad23a` and currently includes substantial integration revision `a2344cc`. Use local file history together with the source commit above when tracing inherited behavior.

## Managed build provenance

Development sessions keep provenance only in the configured private state directory. Schema-2 verified direct builds bind the MCP identity, pre-spawn compiler hash, project identity, effective argument vector and working directory, pre-spawn source byte hashes, optional declarative fixture inputs, absent configuration candidates, and DMB/RSC hashes. Inputs and compiler identity are compared again after compilation. Changed recorded inputs, alias targets, configuration presence, outputs, or a later failed or unverified compile make retained managed artifacts stale. Standard runtime, debugger, and Tracy launch paths share this decision and refuse known-stale artifacts; `require_verified_provenance` also rejects unverified artifacts. HEAD and dirty status are descriptive observations made when the build record is created, not startup observations or extra input-evidence invalidation rules.

Current state uses `artifacts-v2/<location-key>/state.json`. The key identifies the canonical artifact location, independently of the Git common directory and build/attempt IDs. Linked worktrees therefore retain separate records for identical relative DMB names. One atomic replacement publishes the latest attempt and last successful build together. A new attempt is persisted as `in_progress` before compiler spawn; terminal publication must name that same attempt. An abandoned attempt blocks launch even when old DMB bytes remain. The per-location directory preserves the managed marker if publication is interrupted or the state file goes missing. History is bounded to the current attempt and last successful record.

Canonical aliases share one location. Canonical managed artifact paths must be representable as Unicode; lossy path conversion cannot define their identity. Managed artifacts with multiple hard links are rejected. On Windows, canonical ancestor spelling is preserved and only an ASCII artifact filename is case-folded, after checking its containing directory. Case-sensitive Windows output directories and non-ASCII managed output filenames are rejected until their identity semantics are qualified. This does not change source-file naming or grant access beyond startup roots.

Upgrade with all old MCP processes sharing the store stopped. New writers read the legacy `locations`, `builds`, and `attempts` layout without changing it, and retain stale, incomplete, or wrong-location evidence. Missing or damaged managed state requires recovery or rebuild; it never grants unmanaged launch permission. New-format state takes precedence, including an interrupted publication marker. Mixed old/new writers are unsupported. A rollback after newer attempts must retain their invalidation evidence and require fresh builds; restoring an older store snapshot or deleting provenance is not a safe recovery procedure. Storage qualification alone does not establish execution exclusion or completion of crashed child processes.

Verified direct compilation currently supports a conservative ASCII DM subset: unconditional quoted `.dm`/`.dme` includes, scalar unsigned decimal object macros, and unambiguous standalone block comments. Command-line defines, conditionals and other preprocessing, resource literals, backslash escapes/continuations, ambiguous comments, and map/skin/script includes yield explicit unverified reasons. The active parser closure alone is insufficient; every literal include must also be present in that snapshot, and current bytes are captured independently before spawning. Fixture manifests add inputs but do not assert compiler closure completeness. This subset preserves the owned provenance fixture; general game builds remain unverified. Pre/post comparison detects persistent mutations, not a concurrent change-and-restore between observations; it is not filesystem isolation or compiler read tracing.

Schema-1 records remain readable and retain input/output/failed-attempt stale detection, but cannot supply verified launch provenance because effective arguments and pre-spawn evidence were absent. Unsupported verification methods are likewise unverified. These records and artifacts are retained. Rift controller success and artifact validation remain authoritative full-build evidence, but arbitrary generation, nested compiler arguments, and compiler-only resources are not proved by its result, so Rift success does not create a verified build record. Its pre-spawn observed inputs and unverified attempts are retained without replacing the last successful record.

`dm_check_fixture_sync` is read-only. It validates the manifest, required exact proc signatures, required source tokens, and any available managed build state. Fixture manifests contain paths and declarations only: they cannot carry commands, arguments, URLs, globs, environment variables, or out-of-fixture paths.

Fixture manifests are limited to 4 MiB. Declared text inputs (`source`, `generated_binding`, and `configuration`) are limited to 64 MiB each; native modules and service executables to 256 MiB each; all declared inputs to 1 GiB combined. Actual reads are bounded, including files that grow after their metadata is checked. Input size and SHA-256 describe the bytes read; a size or modification-time change during hashing fails validation. These defaults apply to fixture loading in `dm_check_fixture_sync`, `dm_compile`, and `rift_compile`.

Required tokens are literal text matches in declared text inputs. CRLF and LF are equivalent; overlaps and repeated declarations are supported. Token scanning reads each needed file once and checks its size and SHA-256 against the fixture identity. Mixed UTF-8/Latin-1 source is decoded per physical line using SpacemanDMM's fallback. A token must occur wholly within one file. This is text validation, not a DreamMaker lexical-token query or compiled/runtime proof.

Fixture loading, token scanning and fixture-sync provenance checks use the server's bounded blocking-job pool. Temporary fixture parses share the server's parse admission and leave the active analysis snapshot unchanged. Declared-input limits are separate from parsing other project files and from build-provenance input recapture; these checks do not isolate concurrent filesystem edits.

The private state directory must exist outside all workspace roots. A persistent regular lock file supplies operation-scoped cross-process locks for bounded reads, enumerations, and atomic JSON replacement. Multiple MCP processes may share the directory, but only one private-state operation runs at a time, and launch evaluation reads one coherent current record or the related legacy records in one locked transaction. Each active runtime-integrity journal has a separate liveness lock under `runtime-integrity-locks`; recovery ignores a journal whose owner still holds that lock and re-reads the journal after acquiring an abandoned lock before changing its status. Operating-system lock ownership is released when a process or handle exits, including forced termination; persistent lock files are not ownership and do not require stale-file cleanup. MCP tools expose only bounded status and record identifiers, never journal documents or the absolute private-state path. The owned Windows integration fixture writes a separate privacy-validated schema-1 evidence summary; raw compiler/runtime output and private records stay local.

SpacemanDMM crates use baseline revision `351ddc0ffb2439876d4565ce5130bb6b027ee605`, with the locally vendored `meridian-read-policy-v4` delta for `dreammaker` and `dmm-tools`. [Patch provenance and exact delta](../vendor/spacemandmm/README.md) document the actual-open hooks. Parse and status output report both the unchanged upstream revision and the local delta identity. Separately built native helpers retain the unchanged upstream baseline. Tracy helpers are built from Tracy `099df3de3dc37eca4712c06b8320fb9c53596edd` (v0.14.0) and byond-tracy `d1ec404737b04b1ea73d6df4a1b477deacdb1900` (build-d1ec404), using Tracy protocol 82. The builder requires clean source checkouts, copies them into private build roots, applies `tracy-clock-access.patch`, then applies `byond-tracy-empty-queue.patch` and `byond-tracy-health.patch` in that fixed order. It runs all Meridian CTests and records source, patch, x64 helper, and x86 hook hashes in helper-manifest schema v2. Runtime code never downloads or edits these upstream sources.

Tracy is BSD-3-Clause and byond-tracy is BSD-2-Clause. Packaged copies of both license files accompany the native artifacts. The binding/API sources in Tracy are a reference for server internals; Meridian-MCP exposes its own fixed protocol and does not ship the Tracy GUI or Python evaluator/HTTP MCP surface.

The packaged hook applies one Meridian-owned source patch after verifying the upstream Git HEAD: `helpers/tracy/byond-tracy-empty-queue.patch` changes the freshly initialized ring-buffer head from 1 to 0 so an empty queue cannot expose an uninitialized event when the profiler connects immediately. A diagnostic live fixture reproduced the upstream race at `utracy_consume_queue`; repeated post-patch live capture is required before compatibility promotion. Artifact hashes cover the patched binary.

The Windows BYOND 516.1687 hosted gate also needs the legacy x86 DirectX helper imported by DreamDaemon. CI downloads `Microsoft.DXSDK.D3DX` version `9.29.952.8` only from the official NuGet endpoint and requires package SHA-256 `ead0906ae8a26c18a7525da7490127a2110f7c58f18293738283e30e97c6ea4b`. It extracts the unmodified x86 release `D3DX9_43.dll` application-local beside the CI BYOND executables. The package's `LICENSE.txt` and `NOTICE.md` are retained with runtime evidence. This installation is an explicit CI provisioning step; Meridian-MCP startup and MCP tool calls never download or install it.

The over-64K boundary follows BYOND's official [516.1686 release note](https://www.byond.com/docs/notes/516.html), which identifies a DreamDaemon startup crash or hang affecting worlds with more than 64K prototypes. The runtime corpus uses 256-child buckets because a flat 65,537-child parent instead triggers DreamMaker's distinct direct-child ceiling. Synthetic runtime arguments use BYOND's documented [startup options](https://www.byond.com/docs/ref/info.html#/proc/startup): port `0`, loopback `-ip 127.0.0.1`, `-close`, `-log`, `-trusted`, and `-verbose`. Linux ELF binaries do not expose Windows `FileVersionInfo`; the Linux lane therefore records the explicit workflow version backed by the verified archive version and SHA-256, while Windows additionally requires matching PE file metadata. `/tg/station`'s Ubuntu 24.04 [integration workflow](https://github.com/tgstation/tgstation/blob/master/.github/workflows/run_integration_tests.yml) and direct [DreamDaemon launcher](https://github.com/tgstation/tgstation/blob/master/tools/ci/run_server.sh) are the platform authority for the required synthetic engine lane. Meridian-MCP records source declaration counts separately from BYOND-internal prototypes and keeps the Windows synthetic result diagnostic until repeated hosted evidence supports promotion.
