# Architecture

`main.rs` configures the Unix runtime guardian before creating threads, then configures stderr logging and loads immutable `ServerConfig`. `mcp.rs` initializes Windows owner containment and starts the official `rmcp` stdio transport. `MeridianServer` owns the active mode, canonical `PathPolicy`, and shared `ServerState` with separate analysis, runtime, and asset synchronization. Startup expands explicitly configured Git repositories into verified linked-worktree `EffectiveRoot` records before freezing the policy; no tool call can add a root.

The server exposes only contracts active for its startup configuration. Analysis mode contains parsing, indexing, exact lookup, search, diagnostics, and read-only map inspection. Development mode additionally exposes direct compilation, PNG output, DreamDaemon lifecycle, and loopback `Topic()` calls. Windows `rift_compile` is a further conditional contract controlled by the immutable full-build ceiling.

Tool calls cross these boundaries in order:

1. The SDK negotiates MCP, validates JSON-RPC framing, and presents the tool schema.
2. The contract registry decides whether the tool exists in the configured mode.
3. Path policy canonicalizes inputs, checks roots, enforces compiler allowlisting, and requires explicit output overwrite. The local SpacemanDMM read-policy hooks also check derived parser/configuration and map-icon reads immediately before opening them. Source rereads and DMI traversal retain the same startup policy.
4. Domain adapters invoke SpacemanDMM or controlled BYOND operations and return transport-independent results.
5. The server converts domain results to SDK result models.

Direct DreamMaker compilation and Meridian-Rift full builds share bounded output, timeout, platform-specific process cleanup, artifact snapshots, and optional observational endpoint auditing. The generic runner uses Windows Job Object containment; its Unix cleanup targets its owned child, while standard/Tracy DreamDaemon ownership uses the separate guardian described below. Tool modules retain command construction and acceptance semantics. `dm_compile` revalidates the final compiler through the executable policy before spawn. Omitting its path selects the sole configured compiler; empty or ambiguous allowlists return structured errors. `rift_compile` requires a qualified active profile and runs only the canonical `RIFT_BUILD.cmd`, which delegates to the unchanged human build implementation without accepting client-controlled commands.

Development startup opens one private state directory outside every workspace. A persistent regular lock file coordinates operation-scoped exclusive operating-system locks, so multiple MCP processes can share the directory while every bounded read, enumeration, and atomic write remains serialized. Related provenance records are read under one operation lock. Runtime-integrity sessions also hold a separate per-session operating-system liveness lock; startup recovery skips a journal while its owner is live and marks it interrupted only after that lock can be acquired. Lock ownership ends when the file handle closes, including after forced process termination; persistent lock files are not ownership and cannot become stale process locks. Compilation records use atomic schema-versioned JSON. Verified schema-2 direct builds require pre-spawn effective arguments, compiler and complete supported input identities, followed by a stability check. Unsupported preprocessor/resource closure and Rift generation remain explicitly unverified; controller success alone does not certify the compiler input closure. Failed and unverified attempts retain history and invalidate verification of earlier managed artifacts without deleting those artifacts. [Build provenance](provenance.md#managed-build-provenance) defines the supported subset and evidence limits. The shared pre-spawn provenance gate re-hashes the selected DMB and every recorded input: stale managed artifacts are rejected by standard, debugger, and Tracy launchers, while unmanaged artifacts remain explicitly unverified unless the caller requires verification.

`dm_check_fixture_sync` loads a strict contained manifest and checks proc signatures, declared text tokens and available build provenance. It reuses an active snapshot only when the DME and the parser's metadata fingerprint still match, including parsed inputs and configuration discovery. Otherwise it parses into disposable state, preserving the user's active analysis even on failure. This shares the parser's metadata-only freshness limits; same-size changes with preserved timestamps and concurrent edits are not content-identity proof. The tool performs no build or workspace write.

Native evidence ingestion is a separate read-only pipeline. Explicit format adapters stream or bound-read five fixed artifact kinds into records with independent wall, BYOND-world, and local-index time domains. Timeline assignment never interpolates missing clocks. Redaction runs before technical grouping, statistics use deterministic type-7 percentiles, and comparison re-reads all artifacts and validates managed build/workload identity before calculating metrics.

A successful parse builds the context, object tree, compact proc resolver, canonical language/search indexes, and project profile before replacing state. It then advances `state_generation`. A failed parse retains the complete prior generation and reports `state_preserved: true`.

The reuse fingerprint includes every registered input across authorized roots, the requested-to-canonical path mapping, and absent configuration candidates. Required missing inputs prevent reuse. Metadata-preserving byte changes remain outside this metadata fingerprint's guarantee. `dm_get_proc` returns the retained snapshot excerpt, with its generation and an explicit 80-line bound, so it does not mix a previous semantic snapshot with current disk text.

One parse deadline covers admission, snapshot-lock waits, blocking-pool scheduling, fingerprint validation, parsing and publication. The blocking worker owns admission before scheduling and retains it after caller cancellation or timeout until the work ends; expired results cannot publish. Snapshot construction happens in that worker, and failure responses use paired published generation/environment metadata without awaiting the analysis lock. `queue_wait` measures admission; warm `reuse_validation` includes blocking scheduling and delivery; full-build stages measure worker-local work. `total` includes admission and scheduling. These are cooperative deadlines, not hard real-time guarantees for operating-system scheduling or response serialization.

DMI loads use separate worker admission, bounded reads, and a content hash before cache lookup. A cache lock serializes pixel decode and coalesces requests for the same asset. The root PNG adapter bounds metadata and IDAT inflation before allocating pixels. Scans retain one asset per identity and charge aggregate pixel, metadata, state and frame budgets even after LRU eviction. [DMI resource limits](dmi-resource-limits.md) distinguishes those logical residency limits from temporary decoder allocations and total process memory.

The proc resolver stores local implementations, declaration locations, and parent links once per parsed type. Resolution walks that immutable snapshot data on demand, selecting the nearest implementation independently from the nearest declaration metadata. Canonical proc records use the implementation owner; response schemas that need declaration provenance carry a separate declaration owner. This avoids both the former child-override/parent-declaration disagreement and a Cartesian cache of every inherited member on every descendant.

`dm_server_status` is an analysis-safe adapter over immutable configuration plus bounded session state. It reports the exact MCP build identity, active optional gates, `immutable_startup_roots` policy, analysis generation and parsed environment when present, and the owned runtime summary. It may refresh a naturally exited child handle, but it does not parse, spawn, stop, write, or contact a Git remote.

Runtime state contains only a DreamDaemon child created by this server, retained process-tree containment, its loopback port, bounded output, reader tasks, and last exit code. Stop and wait operations cannot target arbitrary operating-system processes. Output and readiness observers clone the original session's output notifications and release the lifecycle mutex while waiting. A replacement runtime cannot satisfy or be stopped by an older session's waiter.

Standard runtime state also owns one private `RuntimeIntegritySession`. Its Git-aware baseline is persisted before spawn; non-Git roots use a bounded manifest fallback. Output observations carry a sequence and monotonic offset, allowing each first-observed mutation to cite the nearest preceding runtime line. A fixed five-second monitor and every explicit lifecycle operation compare against the original baseline. A weak background observer detects natural exit without retaining the runtime while it sleeps. Stop and natural-exit handling retain containment until bounded cleanup confirms termination before integrity finalization; failures leave the journal retryable. Startup inventories unfinished journals without attributing later filesystem state to the dead process. [Runtime ownership](runtime-ownership.md) specifies the Windows Job Object and Linux guardian guarantees, completion checks, and platform limitations.

Tracy is a separately gated runtime kind. Preparation installs a verified x86 hook beside the selected DMB. Launch requires a contained evidence directory, creates a durable integrity journal before starting processes, uses the repository-supported `-params tracy` switch and loopback-only `UTRACY_BIND_*` variables, then starts one schema-2 collector for the runtime lifetime. A drain worker consumes the lossless producer queue; each capture moves through explicit capture-connecting, capturing, validating, and drain-restoring states. One transient handoff is retried within the fixed connection ceiling, capture duration starts only after queue-health readiness, and status exposes the current purpose, retries, queue counters, and hook/prologue validation. The helper reports whether a failed window started and whether draining recovered.

Collector transport uses a single deadline across writer admission, frame write and response, with cancellation-safe bounded request registration and incremental bounded stdout/stderr framing. A separate supervisor owns the actual child and schedules termination before protocol shutdown. Cleanup confirmation is distinct from protocol success; an expired stop keeps ownership and the integrity journal retryable. The generic Unix collector guarantee covers its direct child; the runtime guardian applies to DreamDaemon.

Rust owns both processes, immutable executable/workload identity, exact MCP build identity, request multiplexing, paired trace/sidecar promotion, diagnostic-only invalid artifacts, separate launch-through-stop process-memory series, and the integrity journal. Pre/post lifecycle checkpoints compare only against the initial baseline and exempt exact owned paths. Shutdown always terminates owned processes before final integrity evaluation; a clean final checkpoint finalizes the journal, while a violation leaves it active for recovery without modifying source files. Native offline decoding applies each sidecar's authoritative half-open trace range before frame/zone statistics. Comparison and repeated-control aggregation reject incompatible experiment, workload, role, or MCP build identity before invoking statistics. The Python Tracy MCP, arbitrary expression evaluation, GUI control, and UDP discovery remain outside the product.
